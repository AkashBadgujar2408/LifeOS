# LifeOS — Project Conventions

**`LifeOS_Development_Plan.md` is the main project document** (roadmap, decisions, what's done, and every remaining session to 1.0 — Sessions 34–98 in Section 7; go-live, Session 98, is the last). Session-to-session detail: `PROGRESS.md`. Code map: `docs/ARCHITECTURE.md`; setup/run: `README.md`. Read the plan and the latest `PROGRESS.md` entry at the start of a session. `docs/BLUEPRINT.md` is the original concept (all 20 modules, converted from the Blueprint Word file, which was removed); `LifeOS_Development_Plan.docx` is a stale early copy of the plan — never update or rely on it.

## Stack
.NET 10 LTS Web API (`LifeOS.Core` + `LifeOS.Api`) + Angular 22 (standalone components, Signals). Database: SQL Server LocalDB, database name `LifeOS_UAT` (a separate `LifeOS_Live` gets created only when actually going live).

## Fixed frontend libraries — do not add others without updating the plan doc
Bootstrap 5, ng-bootstrap, @coreui/angular (free tier), ag-Grid Community, SweetAlert2, FullCalendar 7 (`@fullcalendar/angular` + `fullcalendar` + `temporal-polyfill`, Calendar only, Session 16), ng2-charts (Chart.js), Bootstrap Icons, `@ng-select/ng-select` (+ its peer `@angular/cdk`, Session 75b — searchable pickers). Toasts use ng-bootstrap's `NgbToast` through `core/services/toast.service.ts` (`toast.success(...)` / `toast.error(...)`, rendered by the one `<app-toasts />` in `App`) — ngx-toastr was dropped in Session 12 (its latest release only supports Angular 21).

## Backend conventions
- **Areas + per-module folders** (pattern from `OkayToolsEIA4`, confirmed): `LifeOS.Api/Areas/<Module>/Controllers/`, attribute-routed as `api/<Module>/<Controller>`. `LifeOS.Core/<Module>/{DTOs,ServiceContracts,Services,AutoMapper}/` — one interface + implementation pair per domain concern (`IGoalsService`/`GoalsService`). Cross-cutting concerns (Tags/EntityLinks/LifeAreas/Users/Auth) live under the `Shared` module/area, not scattered.
- Controllers are thin; logic lives in Services.
- DTOs + AutoMapper, never return entities (`Models/`) directly from controllers.
- **Database-first**: schema lives in `database/schema/*.sql` (one file per module, each creating its own SQL schema — `goals`, `tasks`, `calendar`, `habits`, `journal`, `shared` — never `dbo`), never EF migrations. Change cycle: edit/add a `.sql` script → apply to `LifeOS_UAT` → `Scaffold-DbContext -force` (exact command in `database/Scaffold-DbContext-Command.txt`) → `LifeOS.Core/Models` regenerates.
- Never hand-edit files under `LifeOS.Core/Models/` — they get overwritten on every re-scaffold. Hand customizations (marker interfaces, computed properties) go in a separate partial class under `LifeOS.Core/Shared/ModelExtensions/`.
- **Dapper + stored procedures** (`database/procedures/*.sql`) for any multi-join/aggregation query (Calendar feed, My Day, Life Balance, later Reports) — deliberate choice so SQL gets learned, not hidden behind LINQ. EF Core stays for simple single-entity CRUD.
- Base columns on every table: `CreatedAt`/`UpdatedAt`, `IsDeleted`/`DeletedAt` (soft delete via global query filter — never hard-delete), all dates/times stored UTC via `SYSUTCDATETIME()`.
- **Multi-user, not single-tenant**: every user-owned table gets a `UserId` column (FK to `shared.Users`) — confirmed with you. `shared.Users` is a real multi-row table populated by registration, not a single seeded account. `LifeAreas` is the one shared/global exception (fixed seeded taxonomy, not personal data, no `UserId`).
- Soft delete is implemented once, centrally: `LifeOS.Core/Shared/ModelExtensions/ISoftDeletable.cs` + a partial-class declaration per scaffolded entity + one reflective global query filter wired through the scaffolded `OnModelCreatingPartial` hook (`AppDbContext.SoftDelete.cs`). New entities just need `public partial class Xxx : ISoftDeletable;` added alongside the others — the filter picks them up automatically, nothing per-entity to configure.
- **Auth exists**: JWT bearer (`Areas/Shared/Controllers/AuthController` — register/login/me), `IAuthService`/`AuthService` using `PasswordHasher<User>`, `IJwtTokenService`, `ICurrentUserService` (reads JWT claims via `IHttpContextAccessor`). Expected business failures (duplicate email/tag name, wrong password, not found) return `OperationResult<T>` (generic `Success`/`Data`/`Error`, `Shared/DTOs/OperationResult.cs`) from the service, not exceptions — exceptions stay for genuinely unexpected errors only, caught by the global handler. Reuse `OperationResult<T>` for every new module's service, don't make a bespoke per-module result type.
- **Per-user query scoping is now global** (added Session 5): `IUserOwned` (`Shared/ModelExtensions/IUserOwned.cs`, just `int UserId`) alongside `ISoftDeletable` — the same reflective filter in `AppDbContext.SoftDelete.cs` combines both (`!IsDeleted && UserId == CurrentUserId`) per entity type automatically. A new user-owned entity just needs `public partial class Xxx : ISoftDeletable, IUserOwned;` — nothing else to configure. `AppDbContext` takes `ICurrentUserService` via a second constructor (in the same partial file, since the scaffolded one can't be touched); EF Core's DI resolves the richer constructor automatically.
- **Race safety on unique business constraints**: a real race was hit in practice during Session 5 (two concurrent create-with-same-name requests) — `CreateAsync`/`RenameAsync`-style methods should catch `DbUpdateException` where `InnerException is SqlException { Number: 2627 or 2601 }` and translate it to the same `OperationResult.Fail(...)` message the pre-check uses, as a safety net alongside (not instead of) the upfront duplicate check.
- `LifeOS.Core` needs `<FrameworkReference Include="Microsoft.AspNetCore.App" />` (not an old standalone NuGet package) for any ASP.NET Core types (e.g. `IHttpContextAccessor`) — the old `Microsoft.AspNetCore.Http.Abstractions`/`Microsoft.Extensions.Identity.Core` NuGet packages are obsolete now that .NET ships these in the shared framework.
- SQL schema script gotchas (`sqlcmd` specific): always `SET QUOTED_IDENTIFIER ON; SET ANSI_NULLS ON;` at the top — filtered indexes (`WHERE IsDeleted = 0`) fail under sqlcmd's default session settings otherwise. Keep index-creation statements **outside** the `IF NOT EXISTS (SELECT 1 FROM sys.tables...)` table-creation guard (check `sys.indexes` separately) so scripts stay safely re-runnable even after the table already exists.
- Use the shared `Tags` entity for all free-form categorization; no bespoke per-module category enums.
- **Calendar dates are `DATE`, moments are `DATETIME2` (UTC)**: target/due dates (`Goals.TargetDate`, task due dates, habit days, journal days) are `DATE` → scaffold to `DateOnly`, serialize as `"2027-12-31"`, and have no timezone to shift. Only "when did this happen" columns (`CreatedAt`, `CompletedAt`, ...) are `DATETIME2` UTC.
- **Tagging a module's entity = a per-module join table** (`goals.GoalTags`, `tasks.TaskTags`, ...): `Id` surrogate PK + `UserId` + FKs to both sides + base columns, with a filtered unique index on the pair (`WHERE IsDeleted = 0`) so untag-then-retag works under soft delete. Not a generic EntityType/EntityId table — that's only for EntityLinks, where the target type is genuinely open.
- **Status/type columns are `NVARCHAR` + named `CHECK` constraints** (e.g. `CK_Goals_Status`), not lookup tables or ints. EF doesn't scaffold CHECK constraints — the database enforces them, so services should validate the same values up front for clean `OperationResult` errors.
- **Watch for join fan-out** when one query pulls two child collections (milestones × tags): in SQL aggregate each child separately (`OUTER APPLY`/subquery), not one `GROUP BY` over both joins (`STRING_AGG` silently duplicates); in EF use `.AsSplitQuery()` or project counts — EF logs `MultipleCollectionIncludeWarning` when this happens.
- **Don't name a table so it scaffolds to a BCL type name**: `tasks.Tasks` would scaffold `Task`, colliding with `System.Threading.Tasks.Task` in every async signature (Session 12) — hence `tasks.TaskItems` → `TaskItem`. Same caution for anything that would become `Action`, `Thread`, `Range`, `Index`, `Environment`, `File`, etc.
- **sqlcmd ad-hoc queries that write to tables with filtered indexes need `-I`** (QUOTED_IDENTIFIER ON), same root cause as the `SET QUOTED_IDENTIFIER ON` rule for scripts. And pass Windows-style paths to `sqlcmd -i` (`cygpath -w` from Git Bash).
- **Name every primary key explicitly** in schema scripts (`Id INT IDENTITY(1,1) NOT NULL CONSTRAINT PK_<Table> PRIMARY KEY`). SQL Server's auto-generated names (`PK__Users__3214EC07...`) differ per database, which makes every re-scaffold churn `AppDbContext.cs`; `PK_<Table>` is also EF's default, so the scaffolder then emits a plain `HasKey(e => e.Id)`. Check after any re-scaffold that `git diff LifeOS.Core/Models` contains only the changes the script intended.
- **All `DateTime`s come back as UTC kind**: a value converter in `AppDbContext.SoftDelete.cs` marks every scaffolded `DateTime`/`DateTime?` as `DateTimeKind.Utc` on read, so JSON always carries the `Z` suffix. Nothing per-entity to do — don't add `SpecifyKind` calls in services.
- **EntityLinks are undirected** ("related to") and stored canonically (ordinally smaller `Type`/`Id` pair is always `Source`) so `UX_EntityLinks_Pair` rejects duplicates in either direction. To make a new entity linkable, implement `ILinkableEntityProvider` (stable `EntityType` string — never rename once data exists — plus `GetTitlesAsync`/`SearchAsync` through `AppDbContext`, so the user/soft-delete filters apply) and register it in `Program.cs` as `AddScoped<ILinkableEntityProvider, XxxLinkableProvider>()`. A module's own delete must call `IEntityLinksService.RemoveAllForEntityAsync(type, id)`.
- **Quick Add → `shared.InboxItems`** (`Kind`: Task/Note/Journal/Idea). When a module that a Kind targets gets built (Tasks, Journal), it adds a "process inbox item into a real X" action that creates the entity and marks the inbox item processed — don't invent a second capture path.

## Frontend conventions
- Standalone components only, feature-folder structure under `src/app/features/<module>`.
- One data-access service per feature wrapping `HttpClient`; no `HttpClient` in components. Import the response envelope type from `core/services/api-response.ts` — don't redeclare `ApiResponse<T>` per service.
- Linkable detail screens drop in `<app-linked-items entityType="Goal" [entityId]="id" />` (`shared/components/linked-items/`); Quick Add (`shared/components/quick-add/`, FAB + `q` shortcut) is mounted once in the shell.
- **Navigation lives in `core/layout/nav-items.ts`** (`NAV_GROUPS`) — the sidebar and mobile drawer both render from it. A module not built yet gets a `placeholder(...)` route in `app.routes.ts` (route `data` → `ModulePlaceholder` inputs via `withComponentInputBinding()`); when the module's session lands, replace that placeholder route with the real `loadComponent` route — never leave a nav entry pointing nowhere. Every route sets a `title` (`'<Page> | LifeOS'`).
- Shell layout CSS lives in `core/layout/shell.scss` (the one layout exception to "utilities over bespoke CSS"). Open Quick Add from code via `QuickAddService.open(kind?)`, not by touching `NgbModal` directly.
- `.btn-outline-primary` has the same CoreUI hardcoded-indigo gotcha as `.btn-primary` (both overridden in `styles.scss`) — check any other `.btn-*`/component variant you introduce for the same thing.
- CommonJS-only libraries (currently `sweetalert2`) go in `angular.json`'s `allowedCommonJsDependencies` so `ng build` stays warning-free.
- Signals for local state, OnPush change detection, reactive forms.
- One shared layout/shell (`core/layout/shell.ts`) wraps every route; style with CoreUI/Bootstrap utilities + shared SCSS partials, not bespoke per-component CSS — exception only for modules that genuinely need custom visuals (Dashboard, Calendar).
- `angular-eslint` + Prettier must pass before a session is considered done. `tsconfig.json` needs `"strict": true` set explicitly — Angular 22's `ng new` no longer sets the bundled flag by default.
- **No `.spec.ts` maintenance** as routine scaffolding — only write/keep tests for components or services with real logic (progress/streak/recurrence calculations, date math), not for templates or thin wrappers.
- `lifeos-web/` lives directly at the repo root (not nested under a `client/` folder).
- `@coreui/coreui/dist/css/coreui.min.css` is the *one* global CSS framework (Bootstrap-compatible superset) — don't also load plain `bootstrap.css`, that duplicates/conflicts with it.
- ag-Grid (v36+) uses the newer JS-based Theming API (e.g. `theme={themeQuartz}` set per-grid in code), not a global CSS theme file — wire it where a grid is actually built, not globally.
- **Heavy lists use `<app-data-grid>` (Session 75a, `core/grid/`)** — never a raw `<ag-grid-angular>`: it carries the theme, 25/50/100 paging (remembered), the phone column set (`[phoneColumns]`, not `hide: narrow`), row open on click/Enter, and Export CSV (filtered + sorted rows of every page, as displayed; `context: { csv }` on a column whose CSV text must differ, e.g. no leading "+"). Columns format days with `dayFormatter(locale)` (`grid-format.ts`) so grid and CSV say `14/Oct/2026`. A Health grid passes `[beforeExport]="healthService.exportGuard('<list>')"` (a new list also needs its key in `HealthExportLists`). A page that keeps cards adds `<app-view-toggle>`. ag-Grid API calls need their API module registered in `data-grid.ts` (`RowApiModule`, `ClientSideRowModelApiModule`, `CellApiModule` so far) — in dev a missing one shows as an "AG Grid found N errors" overlay and the call silently does nothing.
- **Design system (confirmed Session 5, revised same session after visual feedback)**: CSS custom properties in `styles.scss` (`--lifeos-ink #141b2e`, `--lifeos-teal #159895`, `--lifeos-green #57c785`, `--lifeos-canvas #f6faf8`, `--lifeos-border #dce7e3`, `--lifeos-gradient`) are the one source of truth for color — don't hardcode hex values in component templates. Sora (headings) + Manrope (body), loaded via Google Fonts in `index.html`. Cards (`.card`) are the content-grouping unit for interior/content pages (Home, every future module page) — hairline border (`var(--lifeos-border)`), no drop shadow (the generic "SaaS card kit" look is deliberately avoided). **Auth screens (login/register) are different on purpose**: a distinctive full-bleed split-screen (`shared/components/auth-layout/`) with the brand gradient + a real headline on one side, the form on the other — not another centered card, since that's the exact cliché being avoided. The shell's content area has no extra background override — `body` background is set globally via the canvas token.
- **Accessibility (Session 97, WCAG AA, checked with axe on every page)**: text and filled controls in teal use `--lifeos-teal-strong` (#117b78, 4.8:1) — the brand `--lifeos-teal` is only for gradients, borders, icons and charts, never as text or under white text. Danger is `#c73434` (`--cui-danger`, buttons overridden in `styles.scss`), amber is `#8f5e17`, `.text-warning` is the amber, `.btn-outline-secondary` uses `--lifeos-text-secondary`; confirm dialogs use `var(--lifeos-teal-strong)` / `var(--cui-danger)`, never a hex. An `<ng-select>` is named with `labelForId` (a real `<label for>`) or the **`ariaLabel` input** — a plain `aria-label` attribute stays on the host and leaves the input unnamed. Filter pills are buttons with `aria-pressed`, not `role="tablist"`; a `role="list"` needs `role="listitem"` children; a scrolling region gets `tabindex="0"`; an `aria-label` on a `div`/`span` needs a role (`role="img"` for star ratings). Re-run the axe crawl (PROGRESS, Session 97) after visual changes.
- **CoreUI theming gotcha**: `.btn-primary` (and likely other `.btn-*` variants) hardcode their own `--cui-btn-bg`/`--cui-btn-border-color`/etc. directly rather than referencing `--cui-primary` — overriding `--cui-primary` alone does *not* retheme buttons. Override the `--cui-btn-*` custom properties directly on `.btn-primary` (done in `styles.scss`) for any component that doesn't pick up the global primary color re-theme.
- **Auth uses Username for login, not Email** (confirmed, changed from the Session 4 design): `shared.Users.Username` (unique, required, separate from `Email`). Register collects both; Login/`LoginRequest` takes `Username` + `Password` only. If adding more user-facing fields later, check whether they need the same "backfill existing rows" migration pattern used for this (see `database/schema/01_shared.sql`'s upgrade block).
- Reusable cross-feature UI (tag-picker, quick-add, linked-items, entity-reminders, load-error) lives in `src/app/shared/components/<name>/`, is standalone/OnPush, uses signal `input()`/`output()` (not `@Input()`/`@Output()` decorators), and owns its own data fetching via the relevant `core/services/*.ts` — it's not just a dumb presentational component.
- **Every form field must show its own inline validation error** (confirmed bug fix, Session 5) — `markAllAsTouched()` on submit alone does nothing visible without template markup. Pattern: a `fieldError(name)` method on the component returning the message or `null`, `[class.is-invalid]="fieldError('x')"` on the input, and `@if (fieldError('x'); as error) { <div class="invalid-feedback d-block">{{ error }}</div> }` directly below it. Apply this to every new form, not just auth.
- **Every input gets a real `placeholder`** (confirmed convention, Session 5) — not just a label. Write it as an example value or short instruction ("you@example.com", "Choose a username"), never restate the label.
- **One date format everywhere: `14/Oct/2026`** (`dd/MMM/yyyy`, confirmed by you, Session 10). Defined once in `core/dates/date-format.ts`: `DATE_PIPE_DEFAULT_OPTIONS` makes a bare `| date` use it (add a time with `| date: APP_DATE_TIME_FORMAT`), so never hardcode a format string in a template. **Date inputs are ng-bootstrap `ngbDatepicker` text inputs, never `<input type="date">`** (the native picker follows the OS locale and can't show this format). The global `AppDateParserFormatter` displays/accepts `14/Oct/2026` and `IsoDateAdapter` keeps the form value in the API's DATE shape (`"2026-10-14"` / `null`) — pattern: `input-group` with the text input (`ngbDatepicker`, `container="body"`) + a calendar-icon toggle button, and show `dateFieldError(control.errors)` inline for unparseable text.
- **ng-bootstrap needs `@angular/localize`** (`$localize`) — set up in Session 10 via `ng add @angular/localize` (polyfill in `angular.json`, type ref in `main.ts`). Without it, parts of components silently fail to render (the datepicker's month/year header did). If an ng-bootstrap component looks half-rendered, check the console for `$localize is not defined` first.
- **Plain `npm install` works again** (no `--legacy-peer-deps` since ngx-toastr was removed). `vite` is a direct devDependency only so `ng test` (vitest) can resolve it — it was nested under `@angular/build` and `ng test` failed with "vitest package was not found".
- **Inside a form, Enter in a non-submitting text box must `preventDefault()`** (`(keydown.enter)="$event.preventDefault(); ..."`), or it submits the surrounding form — found with the tag picker inside the goal form.
- Goals: status never changes through the edit form — only `PUT api/Goals/Goals/{id}/status` (keeps `CompletedAt` consistent with `CK_Goals_CompletedAt` and logs a `StatusChanged` row to `goals.GoalHistory`). An edit that changes anything logs a `Revised` row (changed field names + target date move + optional `RevisionNote`). History is shown newest-first; future modules wanting an audit trail should follow the same small per-module history table pattern rather than a generic audit log.
- **Task dependencies + focus (Session 45)**: any "A needs B first" graph checks loops with the shared pure `DependencyGraph.WouldCreateCycle` (missions and tasks both) — don't write another. A task's waits are advisory (shown, never enforced) and replaced as a whole on save (`blockedByTaskIds`), so every client save must send them — `TaskPayload` makes them required for that reason. Actual time is always the sum of `tasks.FocusSessions` (never stored on the task); sessions are checked by `TaskTime.CheckSession`. The editor's `<app-focus-timer>` counts by wall clock (`focusedSeconds`), logs on time-up / stop / editor close, and the editor returns `saved` on close when focus time changed so lists refresh.
- **Tasks (Session 13)**: views (Today/Overdue/Upcoming/Someday) are bucketed **client-side** by the user's local date (`features/tasks/task-views.ts`) — the server doesn't know the user's timezone. Anything date-sensitive on the server takes the client's `today` (`PUT …/completed` sends it). Recurring generation lives in `TaskRecurrence` (pure, xUnit-tested): next = first occurrence counted *from the anchor* that's after the completed due date and not before today. Status changes only via `PUT api/Tasks/Tasks/{id}/completed`.
- **Dashboard (Session 22)**: `GET api/Dashboard/MyDay?today&dayStartUtc&dayEndUtc` is one call to `dashboard.GetMyDay` (ten result sets since Session 40 — set 10 is documents expiring soon — read in order with Dapper `QueryMultipleAsync` — keep the C# read order in step with the proc). The `dashboard` schema holds procedures plus, since Session 46, only the user's dashboard *choices* (`KpiTiles`, `DismissedInsights`) — never figures. Computed figures (goal %, streaks) still go through `GoalProgress`/`HabitStreaks` in C#, never SQL.
- **KPIs, dismissals, vision, item titles (Session 46)**: a KPI tile = a `KpiKeys` constant (stable, never renamed) + an entry in `KpiFigures.All` (label, module, unit, compared-with) + `CK_KpiTiles_KpiKey` + a figure in `dashboard.GetKpiFacts`/`KpisService` (windows from `KpiWindows`, local midnights in UTC through the `tz` the client sends). Tiles of hidden modules are filtered client-side (`visibleKpis`) and kept when the picker saves. **Every insight needs a situation `Key`** (`Kind:entity:what-would-change`, built with `Invariant(...)`) — dismissing stores it and My Day hides matching insights, so the key must change exactly when the situation does. Goal progress over time is rebuilt by `GoalProgressTrend` (never stored). The life vision is `Users.LifeVision` via `api/Goals/Vision`, shown by `<app-life-vision>`. **Detail pages call `itemTitle(() => item()?.title)`** (`core/layout/item-title.ts`) so the tab reads "Visit Japan | LifeOS" — every new detail page does the same.
- **Learning (Sessions 47–48; schema `learning`, `10_learning.sql`)**: a skill's level history is `SkillLevelChanges` — create logs the starting level (no "from"), an edit with a different proficiency logs the change on the client's `today` with its note; never rewrite history rows. Course state always goes through `LearningRules.Course` (completing fills today/100%), which mirrors the CHECKs. **Books are Leisure media items since Session 78a** (see the Leisure rule). Linkable types `Skill`/`Course`; deleting a skill nulls the skill on courses/media items/certifications/knowledge notes but leaves study sessions alone (`CK_StudySessions_Subject`). Courses open in their editor (`openCourseEditor`, also from `EntityOpener`); skills have pages. New learning items preselect the Learning life area. **Session 49**: roadmap progress and status go through `RoadmapProgress` (last step finishes, untick/add reopens, Archived untouched); a step points at no more than one course/media item/goal (`MediaItemId`), and those deletes null it (goals too). The certification renewal reminder is owned by `CertificationsService.SyncRenewalReminderAsync` (same rules as document expiry) — don't create renewal reminders elsewhere. Spaced review is only `RevisionPlanner` (1/3/7/14/30, forget = tomorrow, once a day). The study timer is `<app-study-timer [subject]>` (count-up, shares `focus.ts` helpers, logs on stop and on page close).
- **Contacts + Career schema (Session 51; `career` schema, `11_career.sql`)**: `shared.Contacts` is the **one** people list — every module that needs people (Career network, Family) points at it; groupings are tags. Contacts are linkable (`Contact`); a module that references a contact must be released in `ContactsService.DeleteAsync` (it nulls the FK, like job applications' `ContactId`). Interview times live on a `calendar.Events` row (`Interviews.EventId`), not on the interview. Money columns are `DECIMAL(19,4)` + `CHAR(3)` currency checked with `COLLATE Latin1_General_BIN LIKE '[A-Z][A-Z][A-Z]'`. **Session 52**: a promotion only goes through `EmploymentsService.PromoteAsync` (ends the role the day before, new role at the same organisation, Promotion achievement + optional pay, one transaction) — the Life Story leaves out the `NewRole` beat a promotion already tells. Salary change % is `SalaryHistory.FillChanges` on read (same currency and period only), never stored. Money is shown with `formatPay` (`features/career/career-view.ts`). New Life Story beat kinds also need a `beatText` case — the recap renders every beat and breaks on an unknown kind.
- **Applications + interview prep (Session 53)**: an application's stage changes only through `PUT api/Career/JobApplications/{id}/stage`, checked by the pure `ApplicationRules.Move` (dated, not in the future, never before the last move; reaching an applied-for stage fills `AppliedOn`, back to Saved clears it, closing sets `ClosedOn`, reopening clears it) and logged to `ApplicationStageChanges` — the edit form never changes it. A scheduled interview round owns a one-off timed `calendar.Events` row (`Interviews.EventId`, Career life area, title from `ApplicationRules.EventTitle`): `InterviewsService` creates/moves/removes it with the round — never create interview events elsewhere; deleting the event from the calendar unschedules the round (`EventsService.DeleteAsync` nulls `EventId`). EF scaffolds `Event.Interview` one-to-one, so a round's event is **updated in place**. A move to Interview may carry the first round (same transaction). Deleting an application deletes its rounds (and their events) and history; its questions stay in the bank as general ones. Linkable types `JobApplication` (page `/career/applications/:id`) and `InterviewQuestion` (editor). The round form is `<app-round-fields>` + `interview-fields.ts`, shared by the interview editor and the stage-move dialog.
- **Resumes, reviews, side income, network (Session 54)**: a resume version's file is an **attachment** (`ResumeVersion` is in `AttachableTypes`; its delete calls `IAttachmentsService.RemoveAllForEntityAsync` and releases applications' `ResumeVersionId`). Anything dated *in a role* (pay, reviews) is checked with `CareerRules.CheckDayInRole`; career links are checked with `CareerRules.IsWebAddress` (http/https only); side income state with `CareerRules.CheckSideIncome`. The network page is the shared contacts list ordered by `networkOrder` (longest out of touch first, flagged past `CATCH_UP_DAYS`); "in touch today" is `PUT api/Shared/Contacts/{id}/contacted`. The contact editor's Career section reads `GET api/Career/JobApplications?contactId=` — a later module that ties people to its items adds its own section the same way.
- **Mock interviews (Session 54a)**: `career.MockInterviews` is only a **record** of practice done by voice with an AI outside LifeOS (nothing runs or calls an AI here). The rating is free text as the AI said it ("7/10") — never parsed, averaged or scored. Checked by `CareerRules.CheckMockInterview` (client sends `today`); an application delete nulls `JobApplicationId` (general practice); questions to practise are **EntityLinks** (`MockInterview` ↔ `InterviewQuestion`), not a column. The application's "latest rating" is `LatestMockRating` on the application DTO (latest by day held that has one).
- **Finance (Sessions 55–56; schema `finance`, `12_finance.sql`)**: one row per movement of money — Income has only `ToAccountId`, Expense only `FromAccountId`, a Transfer both (`CK_Transactions_Accounts`), so a transfer is never half-recorded. Every transaction is checked by the pure `FinanceRules.CheckTransaction` (amount in the moving account's currency, `ToAmount` for a cross-currency transfer, a manual `ExchangeRate` to the user's `BaseCurrency` — none, so no transaction, until one is chosen; nothing before an account's opening date; nothing new on an archived account). **Balances are never stored**: opening balance + `finance.GetAccountBalances` for the client's `today`. Ledger totals are `FinanceRules.Totals` in the base currency (transfers count in neither income nor spending). Categories are tags (`TransactionTags`, budgets per tag). Money on the client goes through `formatMoney`/`signedMoney` (`features/finance/finance-view.ts`).
